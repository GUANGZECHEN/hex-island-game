# Event-driven local Codex runner

This workflow runs one `codex exec` for an owner-authored open issue when it enters `[READY]`; it does not poll. `opened`, `reopened`, and an edit changing a title from a non-READY state to READY can enqueue work. Events must come from `GUANGZECHEN` on this exact repository and the issue author must also be `GUANGZECHEN`. The job re-fetches the current issue and checks it again before changing `[READY]` to `[WORKING]`. Per-issue concurrency prevents two jobs for the same issue from running at once. An edit already in READY does not start another run; to retry, an owner must intentionally change the title from a non-READY state to READY.

The job deletes only its dedicated `task` checkout inside the runner's GitHub workspace, checks out current `main` afresh, and runs the checked-in runner script. The bootstrap prompt contains only a validated issue number; Codex uses `gh` to read the issue and latest comments as data. The prompt tells Codex not to execute snippets merely because issue text contains them. The workflow never interpolates issue text into a shell. A successful reported PR is checked for an open PR, the correct repository and `main` base, a `codex/issue-<number>-...` branch, and a link to the exact issue before setting `[ARCH-REVIEW]`. A decision result sets `[DECISION]`; other failures set `[BLOCKED]` and post a generic comment. The runner does not merge. If the issue was changed or closed by a person, it avoids intentionally replacing a different state. GitHub's issue update API is not an atomic compare-and-swap, so simultaneous manual title edits can still race with an update.

Codex stdout/stderr and the final structured result are not printed or uploaded: they may contain task or credential data. The result file is removed after the run. This limits troubleshooting and decision details; if a decision is requested, inspect the issue and clarify it manually before retrying. The workflow uses an ephemeral `GITHUB_TOKEN` with contents, issues and pull-requests write access; `gh` and the temporary git credential helper use it for the task. Repository settings must allow GitHub Actions to create pull requests. A token-created PR or push may not trigger other workflows automatically due to GitHub's event-recursion restrictions. No API key is added and no credentials are committed. If GitHub blocks PR creation, the issue becomes BLOCKED; resolve the repository policy or use an explicitly approved alternative rather than silently introducing a long-lived token.

## Security boundary

This is autonomous code execution on a persistent personal machine. The owner gate reduces exposure; it does not make issue instructions, dependencies, GitHub Actions, generated code, or Codex output trustworthy. Codex runs with `workspace-write` and network enabled so it can access GitHub; Windows sandbox behavior and configured local policies must be verified on the installed CLI. Only an explicit environment-variable allowlist is passed to Codex and its shells, including the GitHub token needed for publishing; the runner ignores the user Codex config while retaining its login. The token is available to the task process and an allowed command could exfiltrate it. A workspace path or prompt is not a complete isolation boundary, and a self-hosted runner can access resources permitted to its Windows account. Do not use an administrator account or a profile containing browser data, SSH keys, unrelated credentials or private files. Use a dedicated low-privilege Windows account, a dedicated runner installation and working directory, restrictive filesystem ACLs, and ideally an isolated disposable machine/VM under the owner's control. Do not register the runner at organization level for untrusted repositories or permit untrusted PRs to use its label. Do not use this workflow until the owner accepts and verifies that isolation. No inbound ports are needed; the runner connects outbound to GitHub. Networking to the Codex service and GitHub is necessary; restrict access at the OS/network layer where practical.

## One-time Windows setup after merge

1. Create a dedicated non-administrator Windows account and dedicated runner directory with no unrelated data or secrets. Give it access only to the repository workspace and necessary runtime/login files. Review the security boundary above.
2. Install current Git for Windows, Node.js 24, GitHub CLI (`gh`), and the official Codex CLI for that account. In PowerShell verify `git --version`, `node --version`, `gh --version`, and `codex --version`. The runner script uses `powershell.exe` and the Codex CLI's `exec`, `--ephemeral`, `--sandbox`, `--output-schema`, and `--output-last-message` options; check `codex exec --help` after upgrades. Keep tools outside the checkout directory. Configure a Git author name and an approved GitHub noreply email for this dedicated account so commits can be created without exposing a personal address.
3. While signed in as the dedicated runner account, run `codex login` and authenticate with the existing ChatGPT/Codex account. Verify authentication without printing tokens. Do not set an OpenAI API key. Do not install the runner as a service under a different account before confirming that account can access its own Codex login.
4. In GitHub repository **Settings → Actions → Runners → New self-hosted runner**, choose Windows and follow GitHub's current download and registration instructions into the dedicated directory. Register it for this repository only with the additional label `hex-island-codex`. Do not store the one-time registration token in the repository. Enable Actions and permit Actions to create pull requests in repository settings. Verify branch protection and allowed Actions policies permit the intended PR workflow.
5. Run `run.cmd` interactively as that same Windows account. Confirm the runner is online in repository settings. The machine must remain on and online; queued jobs cannot report an offline runner to the issue because no runner is executing. Optionally install GitHub's runner service only after the interactive test, under the same restricted account, following GitHub's current Windows service instructions. Confirm its Codex login and tool paths independently.
6. To pause, stop `run.cmd` or stop the runner service, or disable/remove the runner in GitHub settings. A queued run may remain pending; cancel it in Actions and reset the issue state deliberately before retrying. Stopping or timing out a job may prevent its cleanup/status update; check `[WORKING]` issues and the dedicated workspace before restarting.

## First-run verification

After merging and finishing setup, create a harmless owner-authored issue titled `[READY] Runner smoke test` that asks only for a reversible documentation change, tests, and a PR, with no secrets or shell snippets. Confirm the issues event queues exactly one job on `hex-island-codex`, and the title changes to `[WORKING]`. Edit unrelated text while it runs and verify no second job starts. Verify the PR targets `main`, links the smoke-test issue, reports tests and unresolved items, and that the issue reaches `[ARCH-REVIEW]`; do not merge automatically. Check Actions logs contain no issue body, prompt or authentication material. Review the PR and runner workspace before continuing. If the job fails, check tool availability, CLI login, repository token policy, sandbox/network configuration and the generic Actions error, then move the issue intentionally from `[BLOCKED]` back to `[READY]` after fixing the cause. If the runner is offline, start it or cancel the queued job; no local process can mark the issue while the machine is offline.

Automated tests can be run with `node --test scripts/codex-runner/tests/*.test.mjs`. These are not a substitute for the first real Windows runner test. This repository change does not install or register a runner and has not executed Codex on a real self-hosted Windows machine.
